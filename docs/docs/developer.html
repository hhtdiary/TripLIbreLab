Developer guide

How TripLibreLab is being built, in the order it is being built: design documents first, then a verified data contract and test fixtures, then the iOS app. This page is for anyone who wants to read, check or continue the work.

i

Where the project stands: the design documents and the SQLite data contract are done, synthetic test databases and a contract checker exist, and no Swift or Xcode code has been written yet. Everything below is checkable from the repository today.

How we build: the order of work

design/first-step.md fixes the order, and the reason for it is simple: the app replays whatever is in TripLibre's database, so nothing can be built with confidence until that database is understood.

  1. Write down the scopeThe framework and first-step documents say what V0.1 does, what it refuses to do, and how it is accepted. They name four normalized models the app will work with: DiaryDay, Trip, Stay and TrackPoint.
  2. Establish the data contract DoneRead TripLibre's real schema and exporter, write down every table, column and convention the app depends on, and map them to the four models. Never invent a column name. The result is the data contract.
  3. Build fixtures and a checker DoneGenerate small synthetic databases from TripLibre's own migration SQL, one per test case in the first-step QA list, and a script that checks any export against the contract without reading personal content.
  4. Build the importer NextA read-only Swift package that opens travel.sqlite, runs the validation checks in the contract, and produces the normalized models. Its unit tests run against the fixtures.
  5. Build the screens PlannedWelcome and import, day picker, replay, share preview, in SwiftUI with MapKit.
  6. QA and release PlannedThe acceptance tests in first-step.md, then App Store metadata and submission.

How the data contract was verified

TripLibreLab had no real export to inspect, and a real export is one person's complete location history, so the contract was derived from TripLibre's source code instead, which is public and Apache 2.0:

QuestionWhere the answer came from (TripLibre repository, version 2.1.0)
Tables, columns, indexes, views, schema versionPackages/HHTCore/Sources/HHTCore/Database/Schema.swift: six append-only migrations tracked in PRAGMA user_version.
How travel.sqlite is writtenTravelStore.backup(to:) runs VACUUM INTO; Exporter.exportBundle calls it with no range filter.
What a "day" is, how trip ends and purposes are resolvedAnalytics.dayKey, Exporter.tripRows, the v_trips view.
Window queries for a dayTravelStore.trips(overlapping:) and visits(overlapping:).
Polyline formatGeo.swift, Polyline.encode/decode: Google encoded polyline, precision 1e-5, (lat, lon).
Code lists (modes, purposes, categories)Models/Enums.swift.
Prose conventionsdocs/data-model.md and the public Data dictionary.

Two behaviours were then tested rather than assumed, by building a database from the verbatim migrations in Python's sqlite3:

  • VACUUM INTO of a WAL-mode database produces a file in rollback-journal mode (header bytes 18 and 19 equal 1). So an export opens read-only with no -wal or -shm files, including from a read-only folder and with immutable=1.
  • The v_trips and v_visits views exist in the output and resolve mode_final, purpose_final and the place fallbacks exactly as the contract describes.
!

Still to do: run the checker on one real export from a phone. Its default output is structure and counts only, no coordinates or names, so it can be pasted into an issue. Until then the contract is verified against source, not against a device.

Tools

Both scripts need only Python 3.10 or newer; there is nothing to install. make help lists every shortcut.

Build the fixtures

python3 tools/make_fixtures.py          # writes fixtures/*.sqlite, deterministic

The script applies tools/triplibre_schema.sql migration by migration, sets user_version after each one, inserts a synthetic Philadelphia day, and finishes with VACUUM INTO, the same call TripLibre's exporter makes. Running it twice on one machine gives byte-identical files; across machines only the SQLite version stamped in the file header changes, which is why CI compares fixtures by content (tools/check_fixtures.py) rather than by bytes.

FixtureCase from the first-step QA list
travel-sample.sqliteValid sample. Schema v6; one day with six trips covering every geometry level, a trip crossing midnight, a stay that is still ongoing, a multimodal trip with segments, a soft-deleted trip, a merged place, a stamp and an expense.
travel-no-gps.sqliteMissing GPS. The same day with no raw points and no polylines.
travel-empty.sqliteEmpty diary. Schema only.
travel-v1.sqliteOldest schema. No places.deleted, no stamps or expenses tables.
travel-future-schema.sqliteUnsupported schema. v6 tables with user_version = 99.
not-triplibre.sqliteValid SQLite with unrelated tables.
not-sqlite.sqliteMalformed file: random bytes.

Check an export

python3 tools/inspect_export.py path/to/travel.sqlite          # structure and counts: safe to share
python3 tools/inspect_export.py path/to/travel.sqlite --days   # also lists diary dates with trip counts
python3 tools/inspect_export.py path/to/travel.sqlite --day 2026-09-15   # one day's timeline: private

The checker opens the file with mode=ro, runs the validation steps in the order the app will (header, quick_check, required tables and columns, version), and exits with status 2 when the file is unsupported. It is the executable form of the contract: when the Swift importer exists, its tests and this script must agree on every fixture.

Configuration lives at the repository root, named as TripLibre names it: package.json, eslint.config.js, .stylelintrc.json, .htmlvalidate.json, .markdownlint-cli2.jsonc, ruff.toml, scripts/a11y.js, vercel.json, and the workflows in .github/workflows/. Two stylesheet blocks are marked with a stylelint-disable no-duplicate-selectors comment: the "notebook" theme layers restyle selectors defined earlier in the same file on purpose, so the base styles stay in step with TripLibre's. New rules outside those blocks are still checked.

When TripLibre changes its schema

TripLibre's migrations only ever add tables and columns, and its codes are never renamed, so an older importer keeps working on a newer export. To keep this repository in step:

  1. Copy the new migration string from TripLibre's Schema.swift to the end of tools/triplibre_schema.sql under a -- ==== migration vN ==== header.
  2. Add a row to the version-history table in docs/sqlite-data-contract.md and to the data contract page; raise the tested-version range in tools/inspect_export.py.
  3. Rebuild the fixtures and check the diff.
  4. If the migration touches trips, visits, places, trip_segments or raw_location_points, update the field map and the importer.

Editing this website

The site is static HTML in docs/, with no build step. Every page is only its <main> content; assets/docs.js adds the header, sidebar, "On this page" outline and previous/next links at load time from one NAV array. To add a page:

  1. Copy an existing page in docs/docs/ and replace the content inside <article class="dx-content">.
  2. Add one entry to NAV in assets/docs.js, and bump the ?v= query on the docs.js script tag in every page so browsers fetch the new navigation.
  3. Use the shared pieces: .callout.note / .warn, .steps, .table-wrap, .cards, and <pre data-lang="bash|sql|python|swift|text"> for highlighted, copyable code.
  4. Mark anything not yet built with Pending, not with a promise. Statements about data that are verified in TripLibre's source but not yet in a real export say so.

The visual design follows the TripLibre website so the two read as one family; change the shared stylesheet only for reasons that apply to both.

Conventions

  • Design before code. If a change is not in design/, update the design document first, or open an issue.
  • No invented data. Column names come from TripLibre's migrations; example values come from the synthetic fixtures. Screenshots appear only when the interface exists.
  • Read-only, local-only. Nothing in this repository may write to a user's export, send it anywhere, or need a network connection to work.
  • Say what is measured. Any geometry the app draws is labelled measured, recorded shape, schematic or gap (see the contract). Code and docs use those four words.
  • Sensitive columns stay on disk. The never-loaded list in the contract (notes, addresses, audit values, booking references) is a rule for the importer, not a suggestion.
  • Python tooling is standard library only. So anyone with a Mac can run it without a virtual environment.

Contributing

  1. Work on a branch and open a pull request against main. Small, complete changes; one topic per PR.
  2. A change to the contract updates the Markdown, this website and, if relevant, the fixtures and checker in the same PR.
  3. Never commit a real travel.sqlite, even a short one. Use the fixtures, or extend make_fixtures.py.
  4. Questions and bug reports go to GitHub issues. Questions about recording and exporting belong to TripLibre.

Decisions waiting on the maintainers

These are recorded at the end of the data contract and will be resolved before the importer is written:

  • Whether an export with a schema version newer than the app knows is imported with a notice (recommended) or refused.
  • Whether the day picker lists only dates with at least one trip (recommended for V0.1) or also dates with only stays.
  • The default redaction settings for the share card.
  • Whether the importer depends on TripLibre's HHTCore package or stays a small read-only package of its own (recommended).
  • Minimum iOS version, bundle identifier, and whether the Xcode project is generated with XcodeGen as TripLibre's is.
